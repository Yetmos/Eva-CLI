# V1.x macOS 下 Codex 自主可解决阻塞项

更新时间：2026-07-26

代码快照：`main` / `ed1f4c1515e5`

环境快照：macOS 26.5.2、Apple Silicon (`arm64`)、Rust/Cargo 1.94.0。当前可用工具包括 `launchctl`、`codesign`、`security`、Homebrew、Docker、GitHub CLI 和 `jq`；PowerShell (`pwsh`) 不可用。

## 1. 目的与口径

本文依据以下材料和当前 owning code path，整理在当前 macOS 主机上可由 Codex 独立推进的剩余工作：

- [V1.x 未完整实现功能清单](V1.x未完整实现功能清单.md)
- [V1.x 真实运行时能力补齐实施计划](V1.x真实运行时能力补齐实施计划.md)
- [V1.x 阻塞项](V1.x阻塞项.md)

“自主解决”必须同时满足：不需要用户提供生产凭据、外部账号、管理员授权、专用硬件或产品决策；可以在仓库和当前用户权限内实现；可以用确定性测试或本机 transcript 验证；执行后不会把局部 macOS 结果误报为三平台或生产 evidence。

本文分为三类：

| 分类 | 含义 |
| --- | --- |
| A：可自主闭环 | Codex 可以完成代码、测试、文档和本机验证，并关闭对应的仓库内或 macOS 子项 |
| B：可自主推进 | Codex 可以补齐与外部设施无关的实现和负向测试，但不能据此解除 production blocker |
| C：不可自主解除 | 缺少外部环境、身份、硬件、权限或获批决策，必须等待用户或组织提供前置条件 |

## 2. A 类：当前可自主闭环

### A-01 修正过时的 Doctor 外部 Adapter 诊断

**状态：实现完成，GitHub Actions 验证中（2026-07-26）**

**对应位置**：未完整实现清单“已知风险 / 过时诊断”；`crates/eva-cli/src/doctor.rs`。

当前 `doctor` 仍输出“V0.3 records placeholders”并建议等待 V1.1 AdapterRuntime，但当前代码已经具备 stdio、HTTP/MCP、Skill、hardware 受控边界和 AdapterRuntime。该诊断会误导操作者，是明确且无外部依赖的本地缺口。

Codex 可完成：

1. 按当前 transport 支持矩阵重写 warning，分别说明可 probe、受控 alpha、配置缺失和不支持的 transport。
2. 增加零 Adapter、多种已知 transport、未知 transport 及 warning JSON 合同回归。
3. 同步中英文文案及 CLI JSON contract（如该字段被固定）。

关闭标准：Doctor 不再引用 V0.3/V1.1 未来态；warning 与当前 AdapterRuntime 行为一致；CLI、contract、fmt 和 Clippy 通过。

完成证据：`external.adapters` 现报告已验证 Adapter 声明、AdapterRuntime 的受控 list/probe 边界，以及 doctor 不执行 provider、不验证生产 transport 依赖的限制；建议直接指向 `eva adapter list`/`probe`。精确回归已加入，fmt 与 diff check 已通过；本机 crates.io 索引无响应且缓存缺少锁定的 `bytes 1.12.1`，完整测试和 Clippy 由本次提交的 GitHub Actions 门禁确认。生产凭据、可执行文件、网络 endpoint 与硬件仍需独立验证。

### A-02 收口 W3-L10 仓库内 daemon-owned provider 生命周期验证

**对应阻塞**：B-P0-02 / W3-L10。

当前代码已在 `eva-runtime::daemon`、`eva-adapter::runtime/supervisor` 和 credential finalizer 中接入长期 owner、关闭准入、provider-before-task drain、绝对 deadline、MCP session/reader/cleanup-pending 零残留门禁。剩余的仓库内验证不依赖真实 KMS 或跨 UID 切换。

Codex 可完成：

1. 审计 renew、restart、shutdown、generation recovery 和二次 drain 的状态机覆盖。
2. 补齐 macOS 真实子进程的 crash-loop、孙进程清理、daemon kill/restart、drain 拒绝新准入和零残留回归。
3. 用临时目录、当前用户 identity 和 Memory vault 生成明确标注为 local/macOS 的 measurement；不得标为 W3 三平台 production evidence。
4. 修复测试发现的 owner、deadline、cleanup 或 PID identity 竞态。

关闭标准：仓库内 W3-L10 行为和 macOS current-identity 子集可重复通过；active provider、MCP session、reader、cleanup pending 和 credential residual 均为 0；文档仍保留 EXT-01、真实 vault 与 W3-L11 production evidence 阻塞。

### A-03 收口 W4-L07 的本地生命周期与故障回归

**对应阻塞**：B-P0-03 / W4-L07 的仓库内部分。

W4-L02 和 W4-L09 已完成，W4-L07 的 owner/drain 已接线。当前 macOS 可以用 loopback TLS/SSE server 和真实 TCP 连接验证 graceful drain、断流、重启 generation、cleanup retry、credential release deadline 和本地 SIGKILL 后客户端残留行为。

Codex 可完成：

1. 强化 loopback server 的 slow-drip、blocked read/write、DELETE 失败、连接断开和 TTL 模拟。
2. 验证 daemon graceful shutdown 后本地资源为零，重启不复用旧 `Mcp-Session-Id`。
3. 验证 SIGKILL 后本地进程资源由 OS 回收，并将远端 session 结果明确标为 fixture observation。
4. 将失败原因固定为稳定 provider code，并补齐负向合同测试。

关闭标准：W4-L07 的仓库内状态机和 macOS loopback evidence 可重复；不得用自建 fixture 替代 EXT-03 命名 server 的 disconnect/TTL 合同或 W4-L10 外部 matrix。

### A-04 收口 W8-L02、W8-L04、W8-L07 的“验证中”代码边界

**对应阻塞**：B-P1-03 / W8 的验证中子项。

这三项已有实现基础：durable schedule/lease、daemon retrieval worker 和 runtime-owned observability lifecycle。其仓库内正确性可以在没有生产 retrieval source、collector 或 database 的情况下闭环。

Codex 可完成：

1. 对 schedule 的 renew、ABA fence、owner crash、过期接管、重启和 shutdown drain 增加真实 daemon 回归。
2. 对默认禁用 retrieval worker 验证 idle、不写 durable knowledge、失败保留 lease、成功才 generation-fenced complete。
3. 对 observability owner 验证启动失败、正常退出、错误退出、flush timeout、重复 shutdown 和 lease release 顺序。
4. 使用 loopback OTLP 或内存 exporter 验证 queue/flush 合同，但只标记为 repository/local evidence。

关闭标准：三项从“验证中”收口为“仓库内完成”；W8-L05/L06、真实 collector、database sink、retention 和 W8-L12 仍由 EXT-05/EXT-09 阻塞。

### A-05 增加当前 macOS 用户域 launchd 的非生产 transcript

**对应阻塞**：B-P0-01 / W2-L05 的 macOS 子集。

仓库已经有真实 `LaunchdAdapter` 和被忽略的 system-domain 原生测试。当前主机具备 `launchctl`，因此 Codex 可以在不使用管理员权限的前提下，使用唯一 label 和用户域 plist 验证 install/status/start/stop/restart/uninstall，并在 finally 中清理。

执行限制：只允许 `gui/<当前 uid>` 用户域、仓库构建产物、唯一临时 label 和可验证 cleanup；不得操作 `/Library/LaunchDaemons`、system domain、已有服务或开机/重启设置。

关闭标准：用户域生命周期和幂等/权限拒绝 transcript 可复验，且无 plist/process 残留。该结果仅关闭 macOS user-domain 本机子项，不能替代 EXT-01 的受控 system service、crash/reboot、三平台 W2-L09/L10 evidence。

## 4. C 类：当前不可由 Codex 自主解除

以下事项不是编码努力可以替代的输入，当前不得纳入“自主完成”承诺：

| 前置项 | 当前缺失 | 为什么不能自主解除 |
| --- | --- | --- |
| EXT-01 | 受控 Windows/Linux/macOS system service host、提权、登录、crash、reboot、跨身份与 finally cleanup | 当前只有一台普通 macOS 用户环境；不能自行获取其他 OS、管理员授权或执行破坏性 reboot |
| EXT-02 | KMS/HSM、key custody、rotation/revocation、plan-trust policy | 需要组织安全决策、生产身份和密钥权限 |
| EXT-03 | 获批的外部 MCP server、固定版本、TLS/auth、disconnect/TTL 合同 | 选择兼容对象和支持范围是产品/运维决策，本地 fixture 不能代替 |
| EXT-04 | 命名硬件或虚拟 fixture、vendor SDK、权限和破坏性边界 | 当前未提供设备、SDK、entitlement 或 fixture identity |
| EXT-05 | Production database、schema ownership、凭据、SLO、retention policy | 需要后端选型和运维责任归属 |
| EXT-06 | CI OIDC、Developer ID/Authenticode/Apt signing identity 与 notarization 权限 | 本机 `codesign` 存在不代表拥有生产证书或 Apple 公证身份 |
| EXT-07 | Homebrew/Winget/Apt 仓库权限、publish token、公开下载地址和 clean runner | 需要外部仓库授权和独立干净环境 |
| EXT-08 | 命名 remote DR store、region/endpoint、credential ref 和 destructive namespace | 需要存储选型、账号与成本/数据策略 |
| EXT-09 | 真实 OTel collector、production retrieval source、版本和故障注入环境 | 本地 Docker fixture 只能证明协议行为，不能批准生产集成 |
| DEC-01 | 获批 production scope | 支持范围和发布责任必须由产品/组织所有者批准 |
| DEC-02 | Registry protocol、认证和信任根 | Codex 可以实现已选合同，但不能替业务选择协议和信任策略 |

## 5. 推荐执行顺序

1. **立即修正 A-01**：范围最小，可消除当前明确误导信息。
2. **并行收口 A-02、A-03、A-04**：这些是已有实现的验证债务，优先把“验证中”变成有边界的仓库内完成。
3. **谨慎执行 A-05**：先补唯一 label、用户域限制和 finally cleanup，再运行真实 launchd transcript；不触碰 system domain。
4. **推进 B 类的合同与负向测试**：优先 W5 基础持久化、W4 matrix validator、W8 retry/queue 和 W10 verifier 内核。
5. **等待 C 类输入后升级 evidence**：外部条件到位时复用已有 harness，生成 production measurement，不重写本地 fixture 逻辑。

## 6. 每项完成时的验证要求

最低仓库基线：

```bash
cargo fmt --all -- --check
cargo clippy --workspace --all-targets -- -D warnings
cargo test --workspace
```

仓库脚本以 PowerShell 编写，而当前主机没有 `pwsh`。Codex 可用 Docker 中的 PowerShell 或先安装 `pwsh` 后运行，但安装新软件不应被默认为任务授权。以下检查在具备 PowerShell 后执行：

```powershell
./scripts/validate-cli-json-contracts.ps1
./scripts/build-site-i18n.ps1
./scripts/validate-i18n.ps1
./scripts/validate-version-management.ps1
```

每个本机 evidence 必须记录 commit、macOS build、arch、Rust toolchain、argv、开始/结束时间、退出码和输出 digest，并明确标注 `local`/`macOS`/`current identity`。不得把以下替代关系写入结论：

- 用户域 launchd 不等于 system-domain service、boot/reboot evidence；
- Memory vault/Keychain 开发 adapter 不等于获批 OS/KMS authority；
- loopback MCP/OTLP server 不等于 EXT-03/EXT-09；
- 伪终端或模拟 hotplug 不等于真实 hardware fixture；
- ad-hoc codesign 不等于 Developer ID 签名和 notarization；
- synthetic ProductionScope 不等于获批 DEC-01。

## 7. 当前结论

当前 macOS 环境最适合自主解决的是：过时 Doctor 诊断、W3/W4 daemon 生命周期验证债务、W8 schedule/retrieval/observability 的仓库内验证，以及受严格限制的用户域 launchd transcript。它还可以显著推进 W5、W7、W8、W9、W10 的通用代码和负向测试，但不能单独解除任何依赖 EXT-01 至 EXT-09、DEC-01 或 DEC-02 的 production blocker。
