## 1. 文档目的与状态口径

本文只保留会阻塞 V1.x **生产能力交付或生产闭环判定**的事项。完成的仓库实现、本地回归和历史 evidence 不在本文记录；如果同一 Work Package 仍缺生产环境验证，只保留尚未解除的边界。

当前公开版本仍为 `1.11.5-alpha`。默认执行 `eva release check --output json` 的事实是：

- `status: "ready"`：当前 alpha 输入没有 required gate 被判定为 blocked。
- `warning_gates: 7`：包含 1 个 service handoff 警告和 6 个未测性能 gate。
- `closure.status: "ready_with_external_blockers"`：生产闭环仍有 5 个明确的外部阻塞项。

因此，alpha `ready` 不等于 production ready，也不能作为 publication decision。

本文件只记录以下三种未闭环状态：

| 状态 | 含义 |
| --- | --- |
| 进行中 | 实现或本地验证已经存在，但要求的生产环境 evidence 尚未齐全 |
| 未解决 | 尚未完成，但已有明确方法且不需要先获得新的外部决策或权限 |
| 阻塞 | 缺少上游逻辑项、获批决策、平台、身份、凭据、硬件或外部服务，当前不能完成验收 |

当前活跃范围映射为 7 个进行中（实施计划中的“验证中”）和 54 个阻塞，覆盖 W2 至 W10。

凡是步骤依赖操作系统服务管理器、进程身份/终止语义、文件系统安全边界、硬件权限或发行渠道，必须同时给出 Windows、macOS、Linux 三个平台的执行方法和平台验收条件。平台表中的状态只描述该平台子边界；任一平台仍为“阻塞”时，不能把所属阻塞项从本清单移除。

## 4. P0 阻塞项与逐步解决方案

**当前状态：阻塞**

当前缺口是受控 host 的真实生命周期、boot/restart/destructive 测试和 production evidence。

| 步骤 | 逻辑范围 | 状态 | 解决方法 | 完成标准 |
| --- | --- | --- | --- | --- |
| 1 | W2-L03 至 L05 三平台真实生命周期 | 进行中 | 在 EXT-01 主机分别执行 Windows SCM、PID1 systemd、launchd user/system 的 install/status/start/restart/stop/uninstall、幂等和权限拒绝；每次使用唯一名称并在 finally 中验证零残留 | 三平台 transcript 绑定 commit、host、executor、service identity、时间戳、argv、stdout/stderr digest 和最终 NotInstalled/disabled 状态 |
| 2 | W2-L08 boot/restart recovery | 阻塞 | EXT-01 提供可 crash/reboot 和外部续接的 host 后，预置 queued work，强杀或重启主机，再验证旧 lease 过期接管、任务完成和 no-double-worker | crash/reboot 后恰好一个 active worker，queued task 只完成一次，旧 PID/lease/control request 不被新 generation 接受 |

### B-P0-02 Provider 用户隔离、真实凭据和生产 evidence 未完成（W3）

**当前状态：阻塞**

当前缺口是生产 service identity 下的 run-as/ownership 证明、真实 secret authority、完整 TOCTOU/leak scan 和 W3-L11 三平台 evidence。默认 alpha evidence 仍明确报告 `provider.os_process_supervisor:not_claimed`。

| 步骤 | 逻辑范围 | 状态 | 解决方法 | 完成标准 |
| --- | --- | --- | --- | --- |
| 1 | W3-L08 原生 run-as 隔离 | 进行中 | 在 EXT-01 service host 使用获批 daemon/provider 账户验证 Unix uid/gid/supplementary groups、root-to-user directory handoff 和 Windows service token；禁止身份提升，Windows 若需跨账户必须先批准并实现 token 创建策略 | 子进程 token/UID/GID 与声明一致，不同账户资源互不可访问，未知/越权 identity 在 spawn 前拒绝，host attestation 可回读 |
| 2 | W3-L09 真实 vault authority | 阻塞 | 选择并批准 Windows OS/KMS、macOS Keychain/KMS、Linux secret store/KMS authority；manifest 只保存 secret ref，按 session acquire/inject/release，并实现 scope/rotation/revocation | 生产默认不再依赖 Memory vault；secret 获取失败 fail closed；session 结束恰好 release；轮换/撤销和错误脱敏通过 |
| 3 | Ownership、TOCTOU 与生产 leak scan | 阻塞 | 在跨身份目录上做 ancestor replacement、symlink/junction/reparse、owner/mode、文件类型和句柄同一性故障注入；用真实 secret canary 扫描 stdout/stderr/log/audit/artifact/stream | 越权或路径竞态在执行/读取前拒绝，真实凭据零命中，扫描 evidence 绑定可信 runner 和 artifact digest |
| 4 | W3-L11 三平台 production evidence | 阻塞 | 在三平台受控 identity host 执行 daemon kill、provider crash-loop、孙进程清理、PID reuse、跨进程 admission、vault revoke、orphan scan；上传后由独立 verifier 回读 | 无 orphan，restart budget/admission/identity/vault ownership 均保持，三平台 evidence 完整且 `provider.os_process_supervisor` 可被 production claim |

**解除标准**：真实 service identity 不越权、真实 vault secret 零泄露、故障后无 orphan、重启不破坏 budget/admission/ownership，并且三平台 production evidence 可独立复验。

**分平台解决方法与验收**：

| 平台 | 当前状态 | 解决方法 | 平台验收条件 |
| --- | --- | --- | --- |
| Windows | 阻塞 | 将 provider 置于获批 SCM service account（默认 LocalService 或批准的专用 SID）下；用 token SID/integrity/privilege 清单和 Job Object 约束子进程，跨 SID 请求在 spawn 前拒绝；凭据通过 Windows OS/KMS authority 按 session acquire/inject/release | 子进程 token 与声明一致且无越权句柄；Job 关闭后后代为 0；DACL/reparse/owner 故障注入均 fail closed；真实 canary 在 stdout/stderr/Event Log/artifact 中零命中，vault release 恰好一次 |
| macOS | 阻塞 | 使用 system-domain launchd 的明确 `UserName`/组边界；在 `fork/exec` 前完成 UID/GID/补充组和目录 owner/mode 校验，采用 process-group 终止与 no-follow 路径检查；生产凭据接入获批 Keychain/KMS，当前用户 Keychain 仅作 local fixture | 子进程 UID/GID/组与声明一致；不同身份不能访问对方目录；ancestor 替换、symlink/mount/firmlink 和句柄竞态均拒绝；强杀后无孙进程/credential residual，Keychain/KMS 错误不泄露 secret |
| Linux | 阻塞 | 在 systemd unit 固定 `User`/`Group`/补充组与 `NoNewPrivileges` 等最小权限，使用 cgroup 作为完整进程边界；用 kernel/secret-store/KMS authority 解析 secret ref，配合 `openat`/no-follow 与 owner/mode 检查 | `/proc`、UID/GID/组、cgroup 和 unit 配置可回读且与 evidence 一致；cgroup 清空后无 orphan，PID reuse/TOCTOU 被拒绝；真实 secret 在日志、审计和制品中零命中，撤销/轮换后 fail closed |

### B-P0-03 MCP 外部生产兼容与远端回收未完成（W4）

**当前状态：阻塞**

当前边界是 W4-L01/W4-L07 的生产外部验证，以及 W4-L10 的命名 server matrix。死亡进程不能主动发送 DELETE，因此 SIGKILL 后的远端 session 回收必须由外部 server 的 disconnect/TTL 合同证明。

| 步骤 | 逻辑范围 | 状态 | 解决方法 | 完成标准 |
| --- | --- | --- | --- | --- |
| 1 | W4-L01 production transport config | 进行中 | 用最终 EXT-03 server 的真实 endpoint、trust root、client auth、redirect/origin policy 复验现有 typed config；凭据只通过已批准 vault ref 获取 | TLS/auth/hostname/CA/redirect/origin 错误稳定，secret 不进入 Debug/audit，禁止回退 cwd 或内联生产 secret |
| 2 | EXT-03 server 与回收合同 | 阻塞 | 产品/运维固定 server 名称、版本、transport、TLS/auth、最大 session TTL、disconnect/SIGKILL 回收语义和可重复环境 | 合同明确死亡客户端无需主动 DELETE 时的回收上限、观察接口和责任方；本地 fixture 不可作为批准对象 |
| 3 | SIGKILL/disconnect/TTL 实测 | 阻塞 | 建立真实 session 后强杀 daemon，分别观测 TCP disconnect、server TTL 到期、credential release、重启 generation 和旧 session 拒绝 | TTL 内远端 session 清零，新 generation 不复用旧 ID，无 dangling stream/reader/credential owner |
| 4 | W4-L10 外部 compatibility matrix | 阻塞 | 实跑 stdio、HTTPS、mTLS/auth、tools/list、tools/call、stream abort、DELETE failure/retry 和 SIGKILL matrix，通过 W0 capture 上传 measurement | 每个 server 记录真实版本/argv/endpoint policy；未运行、TLS 绕过、静态 all-true、缺场景或 residual 非零均阻断 |

**解除标准**：选定外部 server 的 TLS/auth、schema、stream abort、SIGKILL 回收和 TTL 合同全部实跑通过，W4-L10 measurement 可独立回读。

**分平台异常终止与回收方法**：

| 平台 | 当前状态 | 解决方法 | 平台验收条件 |
| --- | --- | --- | --- |
| Windows | 阻塞 | 通过 SCM/Job Object 终止 daemon 和完整子进程边界（不用 Unix `SIGKILL` 字面语义），记录 TerminateProcess/Job 结果后观察真实 server 的 TCP close/RST、TTL 和 credential release | 强制终止后本地 Job/handle/reader 为 0；远端 session 在合同 TTL 内归零，旧 `Mcp-Session-Id` 被拒，新 generation 不复用旧 ID |
| macOS | 阻塞 | 由 launchd 托管进程组，使用 `SIGKILL`/crash 注入并记录 launchd restart generation；通过真实 server 观察 disconnect/TTL，不能把 loopback fixture 当外部合同 | signal、launchd generation、socket close、远端 session TTL 和 credential release 可关联回放；无 dangling reader/stream，旧 session 被拒 |
| Linux | 阻塞 | 由 systemd/cgroup 终止完整 service boundary（`SIGKILL` 只作为注入动作），记录主 PID、cgroup 和 journal，再验证 server disconnect/TTL 与新 generation admission | cgroup 成员清零、journal 有终止原因、远端 session 在约定 TTL 内清零；重启后无旧 session/reader/credential owner 残留 |

三平台都必须使用同一外部 server、版本、TLS/auth policy 和观测接口；平台终止动作不同，不能用单一 `SIGKILL` 文本替代各平台的可回放证据。
