## 1. 目的与口径

EXT-01 在项目计划中的定义是“受控 Windows/Linux/macOS service host”，解除条件包括 destructive service lifecycle、crash、reboot 和 finally cleanup。Windows 本机结果只能作为 EXT-01 的平台子证据，不能单独代表三平台生产闭环。

“自主解决”按以下三类区分：

| 分类 | 含义 |
| --- | --- |
| A：可自主执行或本机闭环 | Codex 可以在仓库和已授权 Windows 主机上完成代码、测试、脚本和本机 transcript；结果必须标注 Windows/local，不能扩大为三平台 evidence |
| B：可自主推进 | Codex 可以补齐实现、harness、validator 和负向测试，但完成判定仍依赖受控 host、外部 authority 或 production gate |
| C：权限之外的外部前置 | 需要组织提供的主机、身份、凭据、信任策略或跨平台环境，单纯提高当前进程权限不能解除 |

## 3. A 类：在明确授权后可自主执行

### A-01 Windows SCM 本机生命周期

在获得提升的管理员 token、唯一服务命名空间和 finally cleanup 授权后，Codex 可以：

1. 补齐 service-aware fixture，使服务入口使用当前 daemon 的 canonical executable、argv、working directory 和 identity digest。
2. 执行唯一服务的 create、status、start、restart、stop、uninstall，并捕获结构化 stdout、stderr、exit code、服务状态和清理结果。
3. 对重复 install/start/stop/uninstall、binary/account drift、权限拒绝、服务消失和 pending delete 生成负向 evidence。
4. 将 transcript 标为 local/windows，并绑定 commit、host、executor、时间戳和摘要。

这可以推进或关闭 W2-L03 的 Windows 本机子项，但只有在受控 host 上产生可回读 transcript 后，才能进入 W2-L10 的 production evidence。

### A-03 Windows harness、validator 和续接脚本

**状态：仓库内 W2-L09 harness 前置和 W2-L10 Windows 本地严格 Lifecycle/Reboot readback validator 已完成（2026-07-28）；受控主机 SCM/reboot 实跑、可信 runner artifact 回读和 production gate 仍待完成**

Codex 可以实现：

1. 使用临时 VM 或受控工作目录的 destructive harness。
2. 以唯一服务名、唯一项目根和 finally 块隔离每次运行。
3. 在重启前写入不可变的 continuation manifest，重启后由外部任务计划、CI runner 或 VM harness 恢复执行。
4. 校验服务、PID、lease、queued work、orphan process 和 artifact 是否全部归零。

当前交互式 Codex 进程本身不会在主机重启后自动存活；要把 reboot 测试变成真正的 autonomous run，必须先提供外部续接机制。

### A-04 Windows provider run-as SID 边界

**状态：repository/local Windows 精确回归已完成（2026-07-28）；受控服务身份、跨账户 token 创建、host attestation 和 ownership/TOCTOU 仍待完成**

W3-L08 的 Windows 代码边界只允许显式账户解析出的 SID 与 daemon primary token SID 完全一致，然后以同一 token 在独立 Job Object 中启动；它不实现任意跨账户 `CreateProcessAsUserW` 或 `CreateProcessWithTokenW`。不同 SID 与无法解析的账户在 `platform::spawn` 之前分别以稳定原因 fail closed。

仓库验证：

    cargo test -p eva-adapter process_backend::tests::windows_ -- --test-threads=1 --nocapture

结果：3 passed、0 failed。same-SID 用例读取真实子进程 token SID，并确认 PID/start token、无 Unix process group、唯一 `Local\\EvaProviderJob-*` identity 和 marker SID 全部成立；different-SID 用例固定拒绝原因为 `provider Windows identity does not match the daemon service token`；unknown-SID 用例固定拒绝原因为 `provider Windows run-as account could not be resolved`。两个拒绝路径都保留 `run_as_kind=windows`，且 marker 不存在，证明命令未进入 spawn。

## 5. C 类：权限之外的外部前置

### 5.1 EXT-01 的三平台范围

EXT-01 本身不是“当前 Windows 机器可用”这一单项条件。解除标准同时要求 Windows、Linux 和 macOS 的真实 service lifecycle、权限拒绝、crash/reboot recovery 和 finally cleanup。即使 Windows 全部通过，也只能解除 Windows 分支，不能把 EXT-01 整体标记为 Complete。

### 5.2 身份、凭据和信任根

管理员权限只授予本机操作能力，不等于：

- 获得可接受的 service identity 或域账户；
- 获得 Windows Credential Manager、DPAPI、KMS/HSM 的生产 authority；
- 获得 CI OIDC、runner attestation 或 evidence signing key；
- 获得生产 gate 对 transcript 的批准；
- 获得产品/组织对跨账户 run-as 和 destructive reboot 的 policy 决策。

当前生产 vault 默认 fail closed，故不能用本机环境变量或 MemoryCredentialVault 伪造生产凭据证据。

### 5.3 破坏性操作的持续性

服务删除、进程强杀和重启会改变主机状态。即使用户明确授权这些动作，也需要：

- 可回滚的独立 VM 或专用测试主机；
- 唯一 service/project/artifact namespace；
- 重启前后都可访问的证据目录；
- 外部 continuation driver；
- finally cleanup 失败时保留现场并使 job 失败的策略。

## 6. 最小授权和环境清单

要开始 Windows 本机 EXT-01 子项，至少需要以下前置条件：

1. 提升后的管理员 token，或明确授予目标测试服务所需的 SCM 权限。
2. 专用 Windows VM/主机，允许安装、启动、停止、删除唯一服务并执行 crash/reboot。
3. 已批准的 daemon service account、service logon right 和测试用 provider account；若只验证 same-SID，必须明确记录这一范围。
4. 重启后续接机制，以及不会随交互式 Codex 进程退出而丢失的 evidence store。
5. 已确定的生产 runner identity、artifact upload/readback executor 和 gate policy；仓库内 Windows 本地 readback verifier 已具备，但不能替代可信 runner 证明。
6. 若验证 W3-L09，提供获批的 Windows OS/KMS vault authority 和不泄露 secret 的 scan 规则。
7. finally cleanup 失败即阻断，不允许用手工删除或 fake adapter 覆盖失败。

## 7. 推荐执行顺序

1. 在专用 Windows VM 上先运行只读 EventLog 和 host capability probe。
2. 以唯一服务名运行 W2-L03 的 install/status/start/stop/restart/uninstall，并在 finally 中确认 NotInstalled。
3. 加入 daemon direct-entry、queued work 和 no-double-worker 检查。
4. 由外部 continuation driver 执行 crash/reboot，并回读同一 generation 的 evidence。
5. 运行 W3-L08 same-SID/不同 SID 拒绝和 ownership/TOCTOU scan。
6. 接入获批 vault 后再运行 W3-L09 secret redaction/leak scan。
7. 最后由独立 verifier 执行 W2-L10/W3-L11 readback；在此之前不得把 Windows local transcript 写成 production evidence。

## 8. 当前结论

在当前机器和当前 token 下，Codex 已安全完成 Windows lifecycle harness 的仓库实现、Windows 本地严格 readback validator、只读/plan-only 验证、只读 SCM 查询和普通 Windows 测试；仍不能直接运行服务变更或重启。

如果提供提升权限、受控 Windows host、唯一 fixture、重启续接和 evidence sink，Codex 可以自主完成 Windows 本机的 service lifecycle harness、Job cleanup 和大部分 transcript 生成。

但“EXT-01 在 Windows 下的阻塞已解决”只有在受控 host 的真实 transcript、身份/ownership 证据、必要的 vault evidence 和 production readback 全部通过后才成立；“EXT-01 整体已解决”还必须补齐 Linux/macOS 分支。权限是必要条件，不是充分条件。
